# ADR 0019: Use progressive context and shared skill routing

- Status: Proposed
- Date: 2026-09-12
- Domains: Shared
- Applies to: Agent-assisted work across MiKode repositories and supported agent hosts

## Context

MiKode's agent context grows from two sources: conversation history and the instructions
loaded while performing a task. The user can keep conversations focused, but that does not
control repeated policy reads, unnecessary skill dependencies, or shared instructions
copied into repository guidance. Skill-driven context therefore needs its own design.

MiKode wants agents to apply the relevant engineering practices consistently while reading
only the context needed for the task. Smaller files alone do not meet this goal if a
workflow still requires all of them. Repository-specific constraints must remain available,
and reducing context must not remove required review or decision steps.

The selected approach needs to work across hosts and repository types. Existing domain
skills remain responsible for their workflows, and engineering remains the authority for
cross-project policy. This decision concerns context selection, not multi-agent execution
or how the user organizes personal conversations.

## Decision

Use progressive context loading with a small shared skill router as the common entry point
when the workflow has not already been selected. A clearly selected domain skill can run
directly without another routing pass.

Select skills from task intent and their discovery metadata before loading their bodies.
Load selected guidance and its required dependencies, and consult current standards or
decision history when the task needs them. Reuse relevant context already resolved for
the task instead of repeating complete workflows.

Keep repository agent guidance focused on local purpose, constraints, risks, commands, and
conditional navigation. Keep shared routing in one maintained source, referenced through
a small entry instruction that the host actually loads. Domain skills retain ownership of
their internal workflow and specialist selection.

The related standard defines the operational contract and adoption criteria. Skill names,
routing tables, host setup, and deployment instructions may evolve without changing this
decision. Introducing a different context-selection strategy would require a new decision.

## Alternatives considered

### Rely exclusively on native skill discovery

Skill descriptions remain useful for discovery and allow a known workflow to run directly.
As the only entry mechanism, they leave workflow precedence and composition entirely to
each host. MiKode chooses a shared router to make that selection more consistent across
tasks and hosts, accepting its maintenance and context cost.

### Repeat shared guidance in every repository

Putting routing tables and shared instructions in each `AGENTS.md` makes them locally
available, but requires repeated maintenance and loads shared detail before its relevance
is known. Local guidance remains necessary; it should reference the shared entry point
instead of reproducing its workflows.

### Load all skills and engineering context at task startup

This makes the available guidance immediately visible, but spends context on unrelated
workflows and historical reasoning. It does not address the user's concern about context
generated by skill use. Required task context should be selected progressively instead.

## Consequences

### Positive

- Tasks can avoid unrelated skill bodies and repeated policy reads while retaining needed
  engineering context.
- Shared selection and precedence can be improved without changing every repository.
- Local guidance, domain workflows, and shared policy retain clear ownership.

### Negative

- The router adds instructions to tasks that need selection and must be maintained as
  available workflows change.
- Reducing context is an intended benefit, not a measured result of this proposal. The
  pilot must compare actual loading and preserved requirements before broad adoption.
- This does not reduce conversation history; keeping conversations focused remains a
  separate practice controlled by the user.
